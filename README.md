# moon_ycrdt

用 MoonBit 实现的、与 [Yjs](https://github.com/yjs/yjs) **二进制格式互通**的 CRDT 库。

MoonBit 程序可以直接读写 Yjs 的更新格式（update format v1）和 y-protocols 同步消息，
与浏览器里基于 Yjs 的编辑器（Tiptap、ProseMirror、CodeMirror 等的 Yjs 绑定）、
y-websocket 服务以及 Yrs 后端交换同一份文档。

> **English summary** — moon_ycrdt is a MoonBit CRDT library that reads and writes
> the Yjs v1 binary update format and the y-protocols sync messages, so MoonBit
> programs can collaborate with Yjs-based editors, y-websocket servers and Yrs
> backends. Text, Map and Array editing produce byte-identical updates to Yjs;
> content it does not model (formatting, embeds, XML, sub-documents) is
> preserved. Every expected value in the test suite is generated by the
> official Yjs packages.

模块 `sayoi7799/moon_ycrdt` · 许可证 Apache-2.0 · MoonBit 黑客松项目 · [更新日志](CHANGELOG.md)

## 定位

本项目不比拼 CRDT 算法，而是做**格式兼容**。Yjs 生态已经有大量编辑器绑定、同步服务和存储后端，
MoonBit 程序只要能产出和消费同样的字节，就能直接接入。因此实现处处以官方 Yjs 的行为为准：
不只是"能互相读懂"，本地编辑产出的每一条更新都与 Yjs 在同样操作下产出的**逐字节相同**，
测试的期望值全部由官方 Yjs 生成。

### 和 MoonBit 生态中已有 CRDT 库的区别

| | moon_ycrdt | [dowdiness/event-graph-walker](https://mooncakes.io/docs/dowdiness/event-graph-walker) | [mizchi/converge](https://mooncakes.io/docs/mizchi/converge) |
|---|---|---|---|
| 算法 | YATA（Yjs 的算法） | eg-walker + FugueMax | 受 EG-Walker 启发 |
| 同步格式 | **Yjs update v1 二进制**、Yjs 状态向量、y-protocols 消息 | 自有的同步消息 | 自有的同步格式 |
| 能否直接和 Yjs / Yrs / y-websocket 交换数据 | 能 | 不能 | 不能 |
| 侧重点 | 互通：字节级兼容 | 算法与文档容器（树、撤销等） | 本地优先同步引擎（含 BFT 校验等） |

（右两列根据各自 mooncakes 页面的描述整理。）它们和本库并不冲突：需要 MoonBit 内部的高级协同功能时
可以选它们，需要和现有 Yjs 系统对接时选 moon_ycrdt。

## 安装

在自己的 MoonBit 项目里添加依赖（需要本模块已发布到 mooncakes.io）：

```bash
moon add sayoi7799/moon_ycrdt
```

然后在用到的包的 `moon.pkg` 里导入需要的子包：

```
import {
  "sayoi7799/moon_ycrdt/lib0",
  "sayoi7799/moon_ycrdt/doc",
  "sayoi7799/moon_ycrdt/types",
  "sayoi7799/moon_ycrdt/protocol",
}
```

## 快速上手

下面的代码与 [`tests/readme_test.mbt`](tests/readme_test.mbt) 中的测试一致，每次 `moon test` 都会运行。

```moonbit
// two replicas, each with its own 32-bit client id
let alice = @doc.Doc::new(1001)
let bob = @doc.Doc::new(2002)

// every local transaction produces a Yjs v1 update, like doc.on('update')
let outbox : Array[Bytes] = []
alice.on_update((update, is_local) => if is_local { outbox.push(update) })

let text = @types.Text::new(alice, "doc")
text.insert(0, "Hello world")
text.delete(5, 6)
@types.YMap::new(alice, "settings").set("theme", String("dark"))
@types.YArray::new(alice, "list").push([@lib0.Any::int(1), String("two")])

// apply updates from MoonBit or Yjs; missing dependencies wait in a queue
for update in outbox {
  bob.apply_update(update)
}
// bob's text is now "Hello"

// state-vector sync: send only what the other side is missing
let diff = @doc.encode_state_as_update(
  alice,
  target_state_vector=bob.encode_state_vector(),
)
bob.apply_update(diff)
```

`apply_update` 遇到格式错误的输入会抛出 `@lib0.DecodeError`，并且不会修改文档。

### 富文本

`Text` 支持格式属性和 Quill 风格的 delta（`toDelta` / `applyDelta`），代码与
`tests/readme_test.mbt` 中的测试一致，期望值由 Yjs 运行同样的步骤得到：

```moonbit
let doc = @doc.Doc::new(1)
let text = @types.Text::new(doc, "doc")
text.insert(0, "Hello world")
// format a range, insert with exactly the given formatting
text.format(0, 5, [("bold", Bool(true))])
text.insert_with_attributes(11, "!", [("italic", Bool(true))])
// a Quill-style delta: skip 6 positions, then insert coloured text
text.apply_delta([Retain(6, []), Insert(String("brave "), [("color", String("red"))])])
// read the formatted text back, as a delta and as JSON
let delta = text.to_delta()
let json = @types.delta_to_json(delta).stringify()
// [{"insert":"Hello","attributes":{"bold":true}},{"insert":" "},
//  {"insert":"brave ","attributes":{"color":"red"}},{"insert":"world"},
//  {"insert":"!","attributes":{"italic":true}}]
let parsed = @types.delta_from_json(@json.parse(json))
```

属性是有序的 `(键, Any)` 列表，值为 `Null` 表示取消该属性。`insert` 不带属性时新文本继承所在位置的格式，
`insert_with_attributes` 则**只**使用给定的格式（没有列出的当前属性会被关掉，插入之后再恢复）。

## 对接 y-websocket

`protocol` 包实现了 y-protocols 的同步消息和 y-websocket 的外层封装。连接建立后的流程
（同样摘自 `tests/readme_test.mbt`，那里用另一个 `Doc` 充当服务端）：

```moonbit
let doc = @doc.Doc::new(42)

// 1. on connect, send SyncStep1 (our state vector)
send(@protocol.Sync(@protocol.sync_step1(doc)).encode())

// 2. broadcast every local change as an Update message
doc.on_update((update, is_local) => {
  if is_local {
    send(@protocol.Sync(@protocol.update_message(update)).encode())
  }
})

// 3. handle every received frame; send back the reply, if any
//    (SyncStep1 is answered with SyncStep2; SyncStep2 / Update are applied)
if @protocol.handle_ws_message(doc, frame) is Some(reply) {
  send(reply)
}
```

`send` 和 `frame` 由所用的 websocket 客户端提供。awareness 等非同步消息由
`handle_ws_message` 忽略，可以用 `decode_ws_message` 拿到原始字节自行处理。

## 可运行示例

**两个副本并发编辑后收敛**，结果以 base64 输出：

```bash
moon run examples/concurrent
```

**Yjs → MoonBit → Yjs 往返**：加载 Yjs 写的文档，用状态向量做差量同步，乱序投递的更新先进入 pending、
依赖到齐后自动应用，最后导出给 Yjs。输入由 Yjs 生成：

```bash
cd scripts && npm ci && cd ..
```

```bash
node scripts/make_example_input.mjs > input.txt
```

```bash
moon run examples/roundtrip -- "$(cat input.txt)"
```

不带参数运行时使用内置的样例文档（同一脚本生成）。

**用 Node + Yjs 读取示例的输出**（示例最后一行是 `update (base64): ...`）：

```bash
node scripts/read_update.mjs "<示例输出的 base64>" doc
```

`read_update.mjs` 做的事情就是：

```js
import * as Y from 'yjs'
const doc = new Y.Doc()
Y.applyUpdate(doc, new Uint8Array(Buffer.from(base64, 'base64')))
console.log(doc.getText('doc').toString()) // "hello, Alice, Bob world"
```

## 协作编辑演示：y-websocket 服务端

`examples/ws_server` 是一个用本库写的 y-websocket 服务端，`examples/web` 是连接它的网页：官方的 `yjs` 和
`y-websocket` 客户端加一个 `<textarea>`。两个浏览器窗口里的文本实时同步，服务端重启后内容还在。

需要：MoonBit 工具链、Node.js 22（网页用 Vite 8 开发服务器）。服务端用 [`moonbitlang/async`](https://mooncakes.io/docs/moonbitlang/async)
（它自带的 `http` 和 `websocket` 包），只支持 native 后端。它的 README 写的是 Linux / macOS，实际上也在 Windows 11
上编译并运行过；CI 在 ubuntu 上跑。因此 `examples/ws_server` 是独立的模块（有自己的 `moon.mod` 和 `moon.work`），
不是 `moon_ycrdt` 的依赖，也不进发布包。

**1. 启动服务端**（在一个终端里）：

```bash
cd examples/ws_server
```

```bash
moon run --target native . -- --port 1234 --data ./data
```

看到 `y-websocket server listening on ws://127.0.0.1:1234` 就绪。参数都可省略：

| 参数 | 默认值 | 含义 |
|---|---|---|
| `--host` | `127.0.0.1` | 监听地址 |
| `--port` | `1234` | 监听端口（y-websocket 的默认端口） |
| `--data` | `data` | 保存文档的目录，不存在会创建 |
| `--save-interval` | `2` | 有改动的房间每隔几秒保存一次 |

**2. 启动网页**（在另一个终端里）：

```bash
cd examples/web
```

```bash
npm ci
```

```bash
npm run dev
```

**3. 打开两个浏览器窗口**，都访问 <http://localhost:5173/?room=demo>。在一个窗口里输入，另一个窗口里文字立即出现；
两边同时输入也会收敛。换一个 `?room=` 就是另一份文档。页面上的状态点是绿色表示已连上服务端。

**4. 验证重启后内容还在**：在服务端的终端按 `Ctrl-C`，再用同一条命令启动，然后刷新浏览器窗口，文字还在。


服务端做的事：

- 连接路径就是房间名（`ws://host:port/<房间名>`），每个房间一个 `Doc`；房间名最长 40 个 UTF-16 码元。
- 新连接先收到服务端的 SyncStep1；客户端的 SyncStep1 由 `handle_sync_message` 回复 SyncStep2；SyncStep2 和 Update
  应用到文档，`Doc::on_update` 把结果作为 Update 广播给同房间的其他连接（不回给发送者）。
- awareness 消息不解析，原样转发给同房间的其他连接。服务端不记录各客户端的 awareness 状态，所以新连接看不到之前
  已在线的光标（演示的网页没有用 awareness）。
- 每个房间保存为 `<data>/<房间名转义后>.ydoc`，内容是 `encode_state_as_update` 的结果，所以可以直接用
  `Y.applyUpdate` 读取。先写 `.tmp` 再改名，中途崩溃不会留下写了一半的文件；第一个客户端进入房间时从文件恢复。
  保存间隔内的改动在进程被强杀时会丢失。
- 没有认证、没有 TLS，只适合本机或可信网络。

网页的 `?server=ws://主机:端口` 可以指向别的服务端，例如用官方的 `y-websocket` 服务端对比。网页里关闭了
`BroadcastChannel`（`disableBc: true`），否则同一浏览器的两个窗口会绕过服务端直接互通，看不出服务端在工作。

编辑器用的是 textarea，不是 Tiptap / ProseMirror：它们的 Yjs 绑定用 `Y.XmlFragment`，本库还没有 `Y.Xml*` 的 API
（见[支持范围](#支持范围)）。

自动化测试 `examples/web/test/e2e.mjs`：启动编译好的服务端，用两个官方 `y-websocket` 客户端验证双向同步、并发收敛、
后加入的客户端、房间隔离、保存的文件能被 Yjs 读取，以及停止再启动服务端后文档仍在：

```bash
cd examples/ws_server && moon build --target native
```

```bash
cd examples/web && npm run e2e -- ../ws_server/_build/native/debug/build/sayoi7799/moon_ycrdt_ws_server/moon_ycrdt_ws_server.exe
```

## API 速查

| 包 | 主要 API |
|---|---|
| `doc` | `Doc::new(client_id)`、`apply_update(bytes)`、`encode_state_as_update(sv?)`、`encode_state_vector()`、`state_vector()`、`on_update((update, is_local) => ...)`、`has_pending()`、`root_names()`；函数形式 `@doc.apply_update`、`@doc.encode_state_as_update(doc, target_state_vector?)`、`@doc.encode_state_vector` |
| `types` | `Text::new(doc, name)`：`insert`、`insert_with_attributes`、`insert_embed`、`format`、`delete`、`to_string`、`length`、`to_delta`、`apply_delta`；`DeltaOp`（`Insert` / `Retain` / `Delete`）、`delta_to_json` / `delta_from_json`<br>`YMap::new(doc, name)`：`set`、`get`、`has`、`delete`、`keys`、`entries`、`size`<br>`YArray::new(doc, name)`：`insert`、`push`、`delete`、`get`、`to_array`、`length` |
| `protocol` | `SyncMessage`（`SyncStep1` / `SyncStep2` / `Update`）的 `encode` / `decode_sync_message`；`sync_step1`、`sync_step2`、`update_message`、`handle_sync_message`；y-websocket：`WsMessage`、`decode_ws_message`、`handle_ws_message` |
| `lib0` | `Encoder` / `Decoder`（`write_var_uint`、`write_var_int`、`write_var_string`、`write_any` 等）、`Any`、`encode_any` / `decode_any`、`to_hex` / `from_hex`、`DecodeError` |
| `update` | `decode_update` / `Update::encode`、`StructRef`、`ItemRef`、`Content`、`DeleteSet`、`encode_state_vector` / `decode_state_vector` |

值统一用 `@lib0.Any` 表示（与 lib0 的 Any 编码一一对应）：`Null`、`Undefined`、`Bool`、`Number(Double)`、
`BigInt`、`String`、`Array`、`Object`（保留键的顺序）、`Bytes`。`Any::int(n)` 构造整数。
文本下标按 UTF-16 码元计算，与 JavaScript 字符串一致。

## 支持范围

| 功能 | 状态 | 说明 |
|---|---|---|
| lib0 编码（varUint / varInt / varString / bytes / Any） | ✅ | 全部有官方 lib0 字节对照 |
| update v1 解码 / 编码 | ✅ | Item、GC、Skip；9 种 content 全部可解码并原样写回 |
| 删除集、状态向量 | ✅ | |
| YATA 冲突解决 | ✅ | 与 Yjs 逐字节一致（见测试） |
| 依赖缺失的更新（pending） | ✅ | 依赖到齐自动应用；`encode_state_as_update` 会带上 pending 数据（中间以 Skip 填补），中继不丢数据 |
| `encode_state_as_update(doc, 状态向量?)` / `apply_update` | ✅ | |
| 事务级增量更新事件 | ✅ | `Doc::on_update`，字节与 Yjs 的 `update` 事件一致 |
| Y.Text 插入 / 删除 / 读取 | ✅ | UTF-16 码元下标；切开代理对时与 Yjs 一样替换为 U+FFFD |
| Y.Text 富文本：带属性插入、`format`、embed、`to_delta`、`apply_delta` | ✅ | 每一步的 delta 和本地更新的字节都与 Yjs 一致；值可以是任意 JSON（对象、数组、数字、字符串、布尔） |
| Y.Text 格式清理 | ✅ | 本地删除后的 `cleanupFormattingGap`，以及远端更新后 Yjs 另开一个事务做的清理（`cleanupYTextAfterTransaction`，产生只含删除的更新）都与 Yjs 一致 |
| Y.Map set / get / delete（`Any` 值、字节数组） | ✅ | |
| Y.Array insert / push / delete / get | ✅ | 定位、值的打包（连续普通值合成一个 Item、字节数组单独成 Item）和 push 的语义都与 Yjs 一致；嵌套类型读作 `Undefined` |
| y-protocols 同步消息与 y-websocket 外层封装 | ✅ | 与 `y-protocols@1.0.7` 逐字节对照；awareness 消息原样透传，不解析 |
| 不支持的 content（XML 类型、子文档、数组中的嵌套类型） | ✅ 保留 | 原样存储并在编码时写回；Yjs 在这些类型内部继续编辑，MoonBit 也能正确合并 |
| Y.Xml* 的 API（包括 y-prosemirror / Tiptap 使用的 `XmlFragment`、`XmlElement`、`XmlText`） | ❌ | 数据会保留。`XmlText` 的格式逻辑与 `Text` 相同，下一步可以复用 |
| 快照、`ychange` 属性 | ❌ | `to_delta` 不支持 snapshot 参数 |
| update v2 | ❌ | |
| 子文档加载、UndoManager、awareness 状态、相对位置、快照 | ❌ | |
| 垃圾回收 | ❌ | 本地文档相当于 `gc: false`，但能解码对方发来的 GC 结构和 ContentDeleted |
| y-websocket 服务端 | 示例 | `examples/ws_server`：native 程序，房间广播和文件持久化，见[协作编辑演示](#协作编辑演示y-websocket-服务端)；不是库的一部分 |
| 编辑器绑定 | 示例 | `examples/web` 里的 textarea 绑定是示例代码；Tiptap / ProseMirror 需要 `Y.Xml*`，❌ |

已知限制：

- **Yjs 的定位缓存（search marker）与带格式的文本**：Yjs 用 search marker 加速定位。不带属性的 `insert` 和
  `delete` 会用它，带属性的 `insert`、`format` 和 `applyDelta` 不用。marker 从目标位置附近开始，看不到它左边的
  格式项，所以带格式的文本里"新文本继承什么格式"取决于 marker 在不在。marker 属于某一个 JS 对象，规律是：
  1. **一个 `YText` 对象一旦整合过任何格式项**（本地的或远端更新里的），marker 就被**永久关闭**，之后所有定位都从头
     累积属性，结果是确定的。先调用 `getText` 再同步更新（编辑器绑定的通常用法）就是这种情形，本库与 Yjs 逐字节一致
     （300 组随机并发场景和各组脚本）。
  2. **例外：根类型在内容到达之后才调用 `getText`。** Yjs 此时用一个新对象替换占位类型：marker 是开着的，而且这个
     对象还没有"含格式"标志，所以不带属性的 `insert` 和 `delete` 看不到 marker 左边的格式；远端更新后的格式清理
     也要等到整合第一个新的格式项才开始。本库按源码实现了这两点，并用一个全新的 marker 模拟 `findMarker`，
     7 个专门设计的场景与 Yjs 一致。但 Yjs 的 marker 会在多次操作之间累积（最多 80 个，位置还随编辑平移），
     本库没有实现，所以连续多次依赖 marker 的操作序列没有被证明一致；"没有含格式标志所以不清理"这一条
     也没有测试覆盖。
- **对象或数组形式的属性值**：Yjs 在格式清理里用 `===` 比较解码出的值。同一个 JS 对象被两个格式项共用时
  （例如 `format` 为恢复旧值会重用已有格式项的值对象）它们被认为相同；编码后的数据里看不出共用，本库把对象和数组
  视为恒不相同。这只影响清理时多余格式项的取舍，不影响文本和格式的收敛。布尔、数字、字符串和 `null` 完全一致；
  "属性是否已经生效"的判断（`equalAttrs`）按 Yjs 的规则只比较一层。
- **属性的键顺序**：属性按给定的顺序写入，和 JS 对象一致，只是 JS 会把整数形式的键（如 `"1"`）排在最前面按数值
  升序，本库没有模拟。
- **delta 里的嵌套类型**：文本里嵌入的共享类型在 `to_delta` 里读作 `Insert(Undefined, …)`；`to_delta` 不支持
  snapshot 和 `ychange`。
- **Yjs 自身的行为**：并发编辑把一个 emoji 切成两半时，各个 Yjs 副本看到的文本可能不一致（一边保留 emoji，另一边是
  两个 U+FFFD），与格式无关。我们在随机测试里观察到过（最初的 300 组里有 14 组），本库不试图修正它。富文本随机测试
  因此把位置限制在字符边界上；代理对被切开的情形由边界情况测试覆盖。
- Yjs 的数组不接受 `undefined` 和 bigint；本库照常把它们编码进数组（Yjs 能解码）。
- 不检测 client id 冲突（Yjs 会在冲突时换 id）。每个副本应使用随机的 32 位 client id，
  `examples/roundtrip` 演示了用 `@env.rand` 生成。
- 定位按链表线性查找，没有 search marker 缓存（见[性能](#性能)）。

## 工作原理

**更新格式**：一条 v1 更新由两部分组成——按 client 分组的 struct 列表和删除集。每个 struct 的第一个字节是
info：低 5 位是 content 类型，`0x80` / `0x40` / `0x20` 三位分别表示有 origin、有 rightOrigin、有 Map 键名。
只有两个 origin 都没有时才写父节点，否则父节点从邻居 Item 继承。删除不占 clock，用"client → (clock, 长度) 区间"
的删除集表示。lib0 的整数是变长编码；有符号整数用"符号位 + 绝对值"（−1 编成 `41`，不是 zigzag）。

**struct store**：每个 client 一个按 clock 连续排列的数组，二分查找定位；需要从中间引用某个 Item 时把它切成两段。
事务结束时把相邻且可合并的 Item 合并回去，只检查本事务改动过的位置。

**YATA**：每个 Item 记住插入时的左邻居（origin）和右邻居（rightOrigin），之后不再改变。integrate 时先在两者之间
找出所有并发插入的 Item：origin 相同时 client id 小的在左；某个 Item 的 origin 落在已扫过的区域里，说明它属于
某个并发 Item 的后续，整段跳过。所以不论更新以什么顺序到达，所有副本得到同一个序列。Map 的每个键是一条
Item 链，最右边的是当前值。

**pending**：依赖（同 client 更早的 clock、origin、rightOrigin、父 Item）缺失的 struct 进入 pending 队列，
每次应用新更新时重试；删除集中还不存在的区间也会挂起。

**本地编辑与 Yjs 一致**：插入的定位规则（例如 Text 会越过右侧已删除的 Item、Array 不会，`push` 接在最后一个
Item 后面）决定了新 Item 的 origin，这些细节都照 Yjs 实现，所以本地更新与 Yjs 逐字节相同。

**富文本**：格式不是"范围标记"，而是和文本放在同一条链表里的 Item（`Format(key, value)`，长度 1，不计入文本长度），
某个位置的属性等于它左边所有格式项依次作用的结果，值为 `null` 表示取消。`insert` 带属性时，先在位置处写入与当前值不同的
格式项，再插入内容，最后写入"恢复旧值"的格式项；已经说了同样的话的格式项会被复用，避免产生冗余。`format` 在范围内
删掉同 key 的旧格式项，范围末尾恢复被覆盖的旧值。冗余的格式项在两个时机被清理：本地 `delete` 之后清理删除区间里的间隙；
远端更新之后，Yjs 会另开一个事务做清理（只含删除的更新，副本之间照常同步），本库照做，所以 MoonBit 副本中继出去的
字节与 Yjs 副本相同。属性值以 JSON 文本保存，和 Yjs 写入线上的格式一样。

## 性能

基准测试在 `benchmarks` 包里，工作负载使用固定种子的伪随机数：

```bash
moon bench -p sayoi7799/moon_ycrdt/benchmarks --target native --release
```

参考数据：AMD Ryzen 9 7945HX、Windows 11、native release，单位为每次运行的平均时间。
"优化前"是事务结束时对整个 client 数组做合并的版本，"现在"只检查本事务改动过的位置。

| 基准 | 优化前 | 现在 |
|---|---|---|
| lib0：编解码 1 万个 varUint 和 1000 个 Any 对象 | 1.80 ms | 1.84 ms |
| 解码并重新编码一个 4000 项的碎片化文档 | 2.96 ms | 2.88 ms |
| 在文本末尾逐字输入 2000 个字符（每字一个事务） | 1.61 ms | 1.77 ms |
| 2000 次随机位置插入 | 96.8 ms | 8.58 ms |
| 4000 字的文本里 1000 次随机删除 | 208 ms | 18.3 ms |
| 加载一个 4000 项的碎片化文档（`apply_update`） | 4.92 ms | 5.94 ms |
| 导出这个文档的完整状态 | 1.66 ms | 1.66 ms |
| 3 个副本 × 300 轮并发编辑并互相同步 | 18.7 ms | 8.82 ms |
| Map：在 100 个键上 set 5000 次 | 430 ms | 5.95 ms |
| Array：push 2000 次再随机插入 500 次 | 13.8 ms | 6.37 ms |

定位仍是沿链表线性查找（没有实现 Yjs 的 search marker 缓存），对很长的文档，随机位置编辑的开销与文档的 Item 数成正比。
